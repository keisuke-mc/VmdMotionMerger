# VMD Motion Merger

複数のMMD用VMDモーションファイルを指定順に連結し、1つのVMDへ書き出すWindowsデスクトップアプリです。
仕様書（MMD VMD連結ソフトウェア 仕様書）の **27章「推奨初期仕様」** をそのまま初期実装として採用しています。

## 採用した仕様（推奨初期仕様に準拠）

| 項目 | 実装内容 |
|---|---|
| 結合対象 | ボーン＋モーフ（カメラ／照明／セルフシャドウ／IK・表示切替は対象外） |
| 境界処理 | 前のVMDの最終フレームの直後へ次のVMDを配置し、フレーム番号をずらして完全連結 |
| クロスフェード | なし（そのまま連続配置） |
| モデル名 | 全VMDで一致必須。不一致の場合は結合前にエラー表示 |
| 重複フレーム | 後のVMD（リストで後ろにあるファイル）を優先して上書き |
| 出力 | 1つのVMDファイル（*.vmd） |

## 技術スタック（前回の EMS プロジェクトと合わせています）

- C# / **.NET 9** / **WinUI 3**（Windows App SDK, MVVM構成）
- CommunityToolkit.Mvvm（ObservableObject / RelayCommand）
- アンパッケージ形式のデスクトップアプリ（MSIXインストール不要、実行ファイルとして配布可能）
- 対象OS：Windows 11（Windows 10 21H2以降でも動作する想定）

もし現在は .NET 10 環境に移行している場合は、`VmdMotionMerger.csproj` の
`<TargetFramework>net9.0-windows10.0.19041.0</TargetFramework>` を
`net10.0-windows10.0.19041.0` に変更してください。

## ビルド方法

1. Windows 11 + Visual Studio 2022（17.9以降）を用意し、
   「.NET デスクトップ開発」ワークロードを入れておく（Windows App SDK 用コンポーネントを含む）
2. `VmdMotionMerger.sln` を開く
3. NuGet パッケージの復元後、スタートアッププロジェクトを `VmdMotionMerger` にしてビルド・実行

> **重要**：このプロジェクトは、WinUI 3（Windows App SDK）に依存しているため
> Windows以外の環境ではビルドできません。今回のコード生成はLinuxサンドボックス上で
> 行っており、実際のコンパイル・実行確認はできていません。まずはお手元のVisual Studioで
> ビルドしていただき、エラーが出た場合は内容を教えてください。

## 実装済み機能（初期リリースの最低限機能：仕様書25章に対応）

- VMDファイルの複数読み込み（「VMDを追加」ボタン／ドラッグ＆ドロップ）
- 読み込み順の変更（上へ／下へ／削除／すべて削除）
- VMDバイナリ解析（ヘッダー・モデル名・ボーンフレーム・モーフフレーム）
- フレーム番号の自動オフセット計算（仕様書6章の計算式：出力フレーム＝元VMDフレーム＋連結先頭フレーム）
- モーション連結（ボーン・モーフ、重複フレームは後優先で上書き）
- VMDとしての再シリアライズ・保存
- エラー表示（ファイル未検出／VMD破損／モデル名不一致／保存失敗／メモリ不足）
- 進行状況・ログ表示（タイムスタンプ付き）

## VMDのバイナリ仕様（実装メモ）

- ヘッダー：30バイト（`Vocaloid Motion Data 0002` = 現行形式／`Vocaloid Motion Data file` = 旧形式）
- モデル名：現行形式20バイト／旧形式10バイト（Shift-JIS）
- ボーンフレーム：1件111バイト（ボーン名15＋フレーム番号4＋位置12＋回転16＋補間曲線64）
- モーフフレーム：1件23バイト（モーフ名15＋フレーム番号4＋ウェイト4）
- 出力ファイルは、初期版で非対応のカメラ／照明／セルフシャドウ／表示枠ブロックを
  件数0として書き出し、VMDとしての構造上の整合性を保っています。

## 未実装・今後の拡張候補（仕様書9章・24章に対応）

- カメラ・照明・セルフシャドウ・IK/表示切替データの結合
- クロスフェード・境界のスムージング
- VMDの分割、モーションのプレビュー、フレーム範囲指定
- コマンドライン版、バッチ処理

## 大容量ファイルに関する注意

現在の実装は、結合対象のフレームを `Dictionary` で名前＋フレーム番号ごとに保持してから
書き出す方式です（重複フレームの「後優先」上書きを単純に実現するため）。
数百万フレーム規模までは通常のPCメモリで問題なく動作する想定ですが、
数千万フレーム級の超大容量を扱う場合は、ストリーミング処理への変更が必要になる可能性があります。
